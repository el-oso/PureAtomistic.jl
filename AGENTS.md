# Repository rules

Plain rules for anyone (human or agent) changing this repository. Each rule carries its reason.

## Scope and layout

- The repository is a monorepo, `PureAtomistic.jl`, with two packages: `PureMLIP/` (the MACE model) and `PureAtomistic/` (the simulation layer on top of PureMLIP). Rules below that name PureMLIP apply to it alone; the rules under "PureAtomistic" apply to the second package, and the code rules, gates, tolerance policy and commit rules apply to both unless a rule says otherwise.
- Each package is self-contained: its own `Project.toml`, `src/`, `test/`, `docs/`. This keeps packages registrable and testable separately.
- PureMLIP has four submodules. `PureMLIP.Checkpoint` (`src/checkpoint/`, entry file `Checkpoint.jl`) reads mace-torch `.model` checkpoints. `PureMLIP.Equivariant` (`src/equivariant/`, entry file `Equivariant.jl`) holds spherical harmonics, Clebsch-Gordan coefficients, Wigner D matrices and the e3nn conversion layer. `PureMLIP.Tensors` (`src/tensors/`, entry file `Tensors.jl`) holds the equivariant tensor kernels (channel-wise tensor product, e3nn linear maps, symmetric contraction) and their pullbacks; it depends on Equivariant and LinearAlgebra only, so it can become a standalone package (PureTensors). `PureMLIP.Model` (`src/model/`, entry file `Model.jl`) builds on the interfaces of the other three: the periodic neighbor list, the checkpoint-to-kernel plumbing and the MACE forward pass. None of Checkpoint, Equivariant and Tensors uses Model, and Checkpoint and Equivariant use neither each other nor Tensors. Reason: the reader and the math change independently, and code built on them depends only on their interfaces.
- A submodule's interface is what it `export`s or declares `public`; everything else is its implementation. `PureMLIP` re-exports the exports of Checkpoint, Equivariant and Model and re-declares their `public` names, so `PureMLIP.x` reaches their interface names; Tensors is reached as `PureMLIP.Tensors.x`, because it is a candidate standalone package and its generic names would crowd the PureMLIP namespace. A name is `public` because other modules or later code use it, not because a test does. Package code outside a submodule uses only its interface. Reason: an implementation detail reached from outside cannot change without breaking the code that reaches it.
- PureAtomistic has seven submodules, each in `PureAtomistic/src/<name>/` with entry file `<Name>.jl`: `Systems` (the atomic configuration), `Potentials` (energies and forces, including the PureMLIP adapter), `Integrators`, `Thermostats` and `Barostats` (the update steps), `Analysis` (quantities computed from a run) and `IO` (reading and writing configurations). The relaxers in `PureAtomistic/src/optimize/*.jl` belong to `Integrators`: `Integrators.jl` includes them, and the layer rule below applies to them as to the rest of it. The layer graph is `Systems → Potentials → {Integrators, Thermostats, Barostats} → Analysis`, and `IO` depends on `Systems` only: each layer may extend functions of the layers it lists and no others, `Systems => ()`, `Potentials => (Systems,)`, `Integrators`, `Thermostats` and `Barostats => (Potentials, Systems)`, `Analysis => (Integrators, Thermostats, Barostats, Potentials, Systems)`, `IO => (Systems,)`. `test_layers` (StrictModeTest) enforces it, and a second item runs ExplicitImports' `check_all_qualified_accesses_are_public` with `allow_internal_accesses = false` on every module. Reason: the layers change independently, and code built on a layer depends only on its interface.
- In-place analysis kernels: `Analysis.rdf!`, `Analysis.msd!`, `Analysis.rmsd!` and `Analysis.reference_sites!` write into caller-provided arrays and allocate nothing; `rdf`, `msd`, `rmsd` and `reference_sites` allocate their outputs and call them. Reason: the analysis of a trajectory allocates nothing per frame, and only the wrapper allocates the result.
- Designs live in `docs/superpowers/specs/`, implementation plans in `docs/superpowers/plans/`.

## Dependencies

- PureMLIP's `[deps]` are Inflate, LinearAlgebra and PrecompileTools, its `[weakdeps]` KernelAbstractions; `[compat]` requires Julia 1.12. The package adds no binary libraries of its own: no `_jll` packages, no artifacts. LinearAlgebra's BLAS backend is OpenBLAS today; it is to be replaced by PureBLAS through libblastrampoline. Reason: binaries block `juliac --trim` builds and portable executables.
- LinearAlgebra and SparseArrays are allowed. Their BLAS and SuiteSparse backends are to be replaced by PureBLAS and PureSparse through libblastrampoline. Reason: the standard libraries stay usable while the pure-Julia backends take over.
- KernelAbstractions is a `[weakdeps]` entry of PureMLIP and PureAtomistic (`PureMLIPGPUExt` and `PureAtomisticGPUExt`, trigger KernelAbstractions, `[compat] KernelAbstractions = "0.10"`) and never a `[deps]` entry. All GPU code lives in those extensions. Metal, CUDA and AMDGPU appear only in the `test/gpu/<backend>/` and `bench/gpu/<backend>/` environments. Reason: KernelAbstractions 0.10 brings 15 `_jll` packages that 0.9.45 does not (a fresh environment holding only KernelAbstractions has 16 `_jll` packages outside the standard libraries with 0.10.5, and 1, LLVMExtra_jll, with 0.9.45). Of the 15, nine come from KernelAbstractions' own PoCL and SPIR-V dependencies (pocl_standalone, Hwloc, SLEEF, XML2, Libiconv, LLVMOpenMP and Xorg_libpciaccess through PoCL; SPIRV_LLVM_Backend and SPIRV_Tools directly), two through Tracy and CompilerCaching (LibTracyClient, LMDB), and four through GPUCompiler (tree_sitter_gcn, tree_sitter_llvm, tree_sitter_ptx, tree_sitter_spirv). They would otherwise enter the core closure and block trimmed builds. The item "core closure is binary-free" resolves a fresh environment holding only the packages and requires that no `_jll` outside the standard libraries and no package with an `Artifacts.toml` appears. It exempts the standard-library `_jll` packages (CompilerSupportLibraries, OpenBLAS and libblastrampoline, which LinearAlgebra brings) on purpose.
- KernelAbstractions 0.10's CPU backend (PoCL, through hwloc) hangs at topology detection on Apple M-series chips that report performance levels: `hwloc_topology_load` spins in `hwloc__darwin_build_perflevel_cache_level` (see https://github.com/open-mpi/hwloc/issues/859). `HWLOC_COMPONENTS=-darwin` makes hwloc skip its Darwin component. On macOS, export it before instantiating or precompiling any environment that holds KernelAbstractions 0.10 (KernelAbstractions' own precompile launches a CPU-backend kernel) and before launching the CPU backend; `test/gpu/runtests.jl` and the mutation runner set it when it is unset. Linux needs nothing.
- PureAtomistic's `[deps]` are LinearAlgebra, PrecompileTools, PureDAQP, PureMLIP, Random, StrictMode, TOML and TypeContracts; `[compat]` requires Julia 1.12. PureMLIP is reached through `[sources] PureMLIP = {path = "../PureMLIP"}` in `PureAtomistic/Project.toml`, and the test and docs projects repeat the path. Every dependency in the package closure is pure Julia: no `_jll`, no artifacts. Makie, AtomsBase, AtomsCalculators and KernelAbstractions enter only as `[weakdeps]` behind extensions. PureDAQP (the step solver of the trust-region relaxers) is pure Julia and passes TrimCheck on the relaxation path, so it is a plain dependency. Optim is used only by `PureAtomistic/bench/`, never by the package. Reason: the core must trim, and the optional integrations must not load for a program that does not use them.
- Test-only dependencies live in `PureMLIP/test/Project.toml` and `PureAtomistic/test/Project.toml` and are exempt. Reason: they never ship in a built program. WignerSymbols is test-only because it fails TrimCheck.
- Every dependency has a `[compat]` bound. Stdlibs are excepted in the test project; the package bounds LinearAlgebra at `1.12` because Aqua's compat check requires a bound for every package dependency. Reason: resolution stays reproducible and Julia 1.12 stays supported.
- No Python in any form: no interpreter, no Python-backed package, no Python-installed stack. When a capability seems to need Python, use a native library through `ccall` or a command-line tool. Reason: the repository targets standalone compiled programs with no interpreter.

## Conventions

- Real spherical harmonics are the textbook ones (reason: one standard convention, with e3nn only at the boundary): z is the polar axis, `m = -l..l`, orthonormal on the sphere, stored at index `l^2 + l + m + 1`.
- Real Clebsch-Gordan coefficients derive from the complex ones with the Condon-Shortley phase. Reason: it is the standard phase, and the tables are checkable against independent references.
- e3nn is reached only through the conversion layer: `Y_e3nn(v) = sqrt(4π)·Y_tb(v3, v1, v2)` and `C_e3nn = s·(M'⊗M'⊗M')·C_tb` with `s = (−1)^((l1+l2−l3)/2)`. Reason: one internal convention, one place where the other is translated.
- Clebsch-Gordan and e3nn coupling are defined only for even `l1+l2+l3`; odd sums throw. Reason: odd sums have no equivariant coupling of this form, so a value would be meaningless.

## Code rules

- Generic indexing: iterate `eachindex`/`axes`, or call `Base.require_one_based_indexing` to declare a 1-based assumption. Tests run entry points on `OffsetArray` and `view` inputs. Reason: callers pass views and OffsetArrays, and a silent 1-based assumption gives wrong answers.
- No `@inbounds` without a benchmark showing the bounds check matters end to end, a local proof of the index range, and a test run under `--check-bounds=yes`. Reason: an unchecked out-of-range access is silent undefined behavior.
- Return types and struct fields are concrete; no `Any` containers. Reason: `juliac --trim=safe` and TrimCheck reject them.
- Functions ending in `!` must not allocate. There are two exceptions. The first is the first evaluation with `ThreadedChunks()` on a `MACEWorkspace`, which starts the workspace's worker tasks (and, with PureBLAS, their task-local scratch); later threaded evaluations allocate nothing (see below). The second is the device `mace_energy!` and `mace_energy_forces!` of `PureMLIPGPUExt`, which allocate host memory on every call for their kernel launches, their matrix products and the read of the status word. Measured on cu_bench(2) with MACE-MPA-0 at the workspace defaults, as the fewest bytes of five calls: on the KernelAbstractions CPU backend 1,168 and 2,400 bytes (Julia 1.12 and 1.13, both precisions); on Metal (Apple M6, Julia 1.13, Float32) 991,408 to 991,504 and 2,007,888 to 2,009,344 bytes, most of it from the symmetric contraction's matrix product per channel (3,008 bytes per Metal `mul!`). "backward: host bytes per call of the device evaluations" gates them per backend as upper bounds: the measured figures on the CPU backend on macOS and twice them on other platforms, where they have not been measured, and 1,000,000 and 2,020,000 bytes on Metal. "backward: device memory does not grow over repeated evaluations" requires Metal's allocated device memory to read the same after 10 and after 210 evaluations. The device `neighbor_list!` belongs to the same exception: on cu_bench(2) with a 6 Å cutoff, as the fewest bytes of five calls, it allocates 0 bytes on the KernelAbstractions CPU backend (Julia 1.12 and 1.13, both precisions), and on Metal 10,048 bytes for a call that rebuilds and 11,760 for one that keeps the list (both launch the same build kernels and read the status word once; keeping adds the launch of the skin criterion). "neighbor list on the device: host bytes per call of neighbor_list!" gates 0 bytes on the CPU backend and 10,100 and 11,800 bytes on Metal. The device MD step of PureAtomisticGPUExt (`step!` of a `Simulation` with a `DeviceMACEPotential`: two kick kernels, a drift kernel, the list rebuild, the evaluation and one read of the status word) belongs to it as well: on the tiny checkpoint's three atoms, as the fewest bytes of five steps, it allocates 2,464 bytes on the KernelAbstractions CPU backend (Julia 1.12 and 1.13, both precisions) and 456,736 to 456,928 bytes on Metal (Apple M6, Julia 1.13, Float32); "md step: host bytes per step" gates 2,464 bytes on the CPU backend on macOS and twice that elsewhere, and 460,000 bytes on Metal, and "md step: device memory does not grow over 1,000 steps" requires Metal's allocated device memory to read the same after 10 and after 1,000 steps. With MACE-MPA-0 on 32 Cu atoms a step allocates 2,400 bytes on the CPU backend and 2,020,576 to 2,021,840 bytes on Metal (fewest of five; a measurement, not a gate), the evaluation's figures above. A step with the device Bussi or Langevin thermostat or the Berendsen barostat (its kernels for the Philox draws, the device kinetic-energy sums, the velocity scaling or the O step, and the pressure) allocates the same 2,464 bytes on the CPU backend (Julia 1.12 and 1.13, both precisions) and on Metal at most 462,384 (Bussi), 458,656 (Langevin), 461,104 (barostat), 465,936 (Bussi and barostat) and 462,272 bytes (Langevin and barostat) as the largest fewest-of-five over 12 groups in 3 processes; "thermostats: host bytes per thermostatted and barostatted step" gates 2,464 bytes on the CPU backend on macOS and twice that elsewhere, and 470,000 bytes on Metal. A step reads one status word back, and the barostat one pressure; a step whose edges outgrow the list (5 % spare edges by default: on Metal at cu_bench(14) 10 % spare edges cost 5.6 % per evaluation, so 5 % costs about 2.8 %, while a regrowth is cheap, 8 ms against 68 ms for an evaluation of 500 Cu atoms, and is logged; `PureAtomistic/bench/results/gpu_capacity_margin_metal.json`) reads it twice and builds a new list, which reads its edge count and status word back as well, and a new workspace, while the old ones stay allocated until the garbage collector frees them. Reason: they sit in hot loops, where every allocated byte brings the next garbage collection closer; the CPU entry points allocate nothing, while a device evaluation cannot avoid the host objects of its kernel launches and matrix products (on Metal about 1 to 2 MB per evaluation of MACE-MPA-0), so their bytes are held to the measured figures as upper bounds, and a growth shows up as a failing gate.
- Fail fast: errors are `ArgumentError` or carry a module prefix (`"checkpoint: ..."`, `"unpickle: ..."`). No silent fallbacks. Reason: unexpected input should surface where it occurs.
- Use `lazy"..."` for interpolated messages with four or more pieces. Reason: it keeps error construction trim-compatible.
- Comments describe the code as it is: invariants, non-obvious reasons, constraints. No history, plans, or task references. Reason: a reader has only the repository. Code ported from MIT-licensed work carries an attribution comment.

## Gates

- Tests are `@testitem`s run by TestItemRunner, with shared setup in `@testmodule`s. Reason: each item can run alone.
- Value items check results against oracles (see below); `OffsetArray`/`view` items check generic indexing; error items check each fail-fast message with `@test_throws "message"`. Reason: each kind of item proves a different property, and no one kind substitutes for another.
- `TrimCheck` `@validate` and `StrictModeTest` `test_signatures(:typestable)` each cover every exported function of `PureMLIP` and of `PureMLIP.Tensors` (the Tensors functions in Float64 and Float32, with `Base.return_types` checks; the exported types are not checked) plus the internal entry points `embedded_archives` and `entry_data`; the type-stability list also covers `open_torch_archive` and `unpickle`. A new exported function is added to both lists. Reason: inference failures are what `juliac --trim` rejects.
- `test_layers` (StrictModeTest) checks the layer graph `PureMLIP => (Checkpoint, Equivariant, Tensors, Model)`, `Model => (Checkpoint, Equivariant, Tensors)`, `Tensors => (Equivariant,)`, `Checkpoint => ()`, `Equivariant => ()`: no module adds a method to a function owned by a module it does not declare. Its qualified-access rule also judges reads between modules of one package (it requires StrictModeTest >= 0.5.4, and the test environment requires 0.5.10; it passes `allow_internal_accesses = false` to ExplicitImports). A separate item is an independent second check of the same rule: it runs ExplicitImports' `check_all_qualified_accesses_are_public` on `PureMLIP`, `Checkpoint`, `Equivariant`, `Tensors` and `Model` with `allow_internal_accesses = false` and `from = (PureMLIP,)`: package source may read only `export`ed or `public` names of PureMLIP's modules. Reads of Base, Core and other packages are not judged, and neither are test files; tests may reach internals by full path (`PureMLIP.Model.zbl_edge_energy`). Reason: the submodule boundaries hold only while something checks them.
- `test_calls` (StrictModeTest) sweeps each submodule (Checkpoint, Equivariant, Tensors, Model) after the item has called its entry points, and requires the sweep to be non-empty: no compiled signature may carry a `MethodError` or `UndefVarError` report. An exemption names one function, with its reason in the commit body. Reason: a call that cannot resolve on an untested branch passes every other gate.
- `Aqua.test_all(PureMLIP)` runs with every sub-check enabled (ambiguities, unbound type parameters, undefined exports, project comparison, stale dependencies, compat bounds, piracy, persistent tasks). Reason: these defects are mechanical to find and costly to find late.
- `@test_noalloc` covers `spherical_harmonics!`, `spherical_harmonics_and_gradient!`, `e3nn_spherical_harmonics_and_gradient!`, `neighbor_list!`, and `mace_energy!` (with a `MACEWorkspace` and with a `MACEEnergyWorkspace`) and `mace_energy_forces!` in Float64 and Float32, each `MACEWorkspace` with one and with four receiver chunks (`nchunks`). With `ThreadedChunks()`, once the workspace's workers have started, the gate requires the fewest bytes of five evaluations of each `MACEWorkspace` entry point (after two) to be 0, in a child process on four threads, for 1 to 35 chunks in both precisions. It is the minimum because a single evaluation can allocate up to 192 bytes more when a thread first runs a function in a task (an entry in the runtime's method cache). The gate runs with OpenBLAS in "forces: threaded chunks give the serial chunk result" and with PureBLAS in "PureBLAS: threaded chunks give the serial chunk result". The first threaded evaluation of a new workspace, which starts the workers, is gated in the same child for 2, 4 and 8 chunks, as the bytes of `@allocated` inside a function: with OpenBLAS exactly on macOS arm64, where it was measured (5,664, 7,808 and 12,432 bytes, the same in both precisions and both entry points; 384, 1,152 and 2,688 bytes for the first evaluation after `close(ws)`), and as an upper bound of twice those figures on every other platform; with PureBLAS within a range on macOS arm64 and as an upper bound of twice the largest total seen elsewhere, because its total varies between processes (see `docs/src/model.md`). The steady-state `== 0` gate holds on all platforms. Other `!` functions are not gated yet.
- `StrictMode.conversion_report(M; from = Float32, to = Float64)` (StrictMode >= 0.5.8; the test environment requires 0.5.10) is swept over `PureMLIP.Model`, `PureMLIP.Tensors` and `PureMLIP.Equivariant` after the Float32 and Float64 evaluation paths have run, and no function may convert Float32 data to Float64 except, in Model, `#neighbor_list#1` and `_check_inputs` (the Float64 `r_cut` meets Float32 values) and `polynomial_cutoff` and `_poly_envelope` (Base's integer power widens inside Base). `_check_inputs` is `@noinline` so that its widening is not attributed to `mace_energy!`. Reason: `:typestable` and the return types accept a kernel that computes in Float64 and returns a Float32, because every way of handing back a `T` converts at the boundary; only the conversion instruction shows it. The `Base.return_types` checks stay: they pin the exact return type, which the conversion sweep does not.
- `test_compiled(M; guarantees = (:no_threadid_state,))` (StrictModeTest >= 0.5.7) sweeps Model, Tensors and Equivariant after the Float32 and Float64 evaluation paths have run, and requires each sweep to be non-empty: no compiled signature may store into a buffer indexed by `Threads.threadid()`. Reason: a store like that is a data race once tasks migrate between threads. The scan reads one signature's IR and does not follow a call the optimizer left out of line, so the sweep over every compiled signature, not a check of the entry points, is what covers the callees.
- `StrictMode.audit(M; sweep = true, guarantees = (:concurrency_safe,))` (the test environment requires 0.5.10) sweeps Model, Tensors and Equivariant after both precisions and both workspaces (`MACEWorkspace`, `MACEEnergyWorkspace`) have run, and requires each sweep to hold `:concurrency_safe` findings and none with status `:fail`. `:info` findings are allowed: they mark a call the scan could not resolve, or a `!` function whose argument 1 is its output, which includes a function whose argument 1 is a closure that writes the buffers it captures, and the worker functions of `src/model/workers.jl`, whose argument 1 is the shared state of the workers. Such a function ends in `!`, or the sweep reads it as a `:fail`. Reason: the scan reads a store into argument 1 of a non-`!` function as a write to a plan shared between tasks, and a `:fail` is a write it read. `:concurrency_safe` is not in the `:all` policy set, so the sweep names it.
- `StrictMode.resource_leak_report(PureMLIP.Model)` runs with `MACEWorkspace`, `MACEEnergyWorkspace` and `NeighborList` registered by `register_scoped!`, and only the constructors and `neighbor_list!` (which returns the list it was given) may return one. Reason: an evaluation function that returned, stored or task-captured a borrow of the caller's workspace would outlive its owner. The report is `:info` and cannot follow a callee, so the item asserts on the findings itself.
- StrictMode policy (PureAtomistic): `@strict_policy (:typestable, :noalloc)` is the last statement of `Systems`, `IO` and `Analysis`; it must stay last, since it checks the methods defined above it, and at precompile time it checks only the methods whose signatures are concrete (`:typestable` throws, `:noalloc` warns). `Potentials`, `Integrators`, `Thermostats`, `Barostats` and the top module declare `@contract`s and carry no policy until TypeContracts stops allocating in the contract specs it generates (https://github.com/el-oso/TypeContracts.jl/issues/4; the item "TypeContracts specs pass the allocation scan" is `@test_broken` until then), but their code meets the same policy. `@strict_exempt` is allowed only for entry points (constructors, `run_md` and its config parsing, `relax!`, `neb`, the IO readers and writers, the allocating analysis wrappers `rdf`, `msd`, `rmsd`, `coordination_numbers`, `reference_sites` and their helpers) and for workspace creation and regrowth (`_sized_list`, `_regrow!`, `_log_regrow`), each narrowed to `:noalloc` with a present-tense reason naming its kind. The exemption of `:_` covers the keyword bodies of parametric constructors, which Julia names `#_#N`; an item requires every such method to be a constructor. The item "StrictMode policy holds in every module" runs `test/strict/workload.jl` in a fresh process and requires, for every module, `test_compiled(M; guarantees = (:typestable,))` (JET) and an `audit` sweep for `:noalloc` (the value-free scan, with `_regrow!` registered as a barrier) to find nothing; `@test_noalloc` items prove the hot paths with AllocCheck. A new function in a hot path is added to the workload. Reason: a module states its guarantees in its source, and the sweep over compiled specializations is what covers the generic methods the precompile-time check cannot.
- The juliac item (tag `:juliac`) builds `PureMLIP/juliac/build/bin/mace_inspect` with `--trim=safe` and runs it on MP-0b3. A second juliac item builds `mace_threads` from `juliac/entry_threads.jl`, which evaluates forces on the tiny checkpoint with `ThreadedChunks()` on 2 chunks and 2 threads (`JULIA_NUM_THREADS=2`, since `-t 2` reaches the program as an argument), and requires the output to equal the untrimmed run bit for bit and the process to exit within a timeout, with the workspace closed, left open, and dropped (the finalizer stops the workers). Both items write the build output to a log file, print it, and require that no line contains "unresolved call" or "Error #", since the trim verifier still writes the executable when it reports findings. They run only with `PUREMLIP_JULIAC_BUILD=1`. Reason: they prove the whole program trims, which per-function checks cannot, but it is slow.
- The PureAtomistic juliac item (tag `:juliac`) builds `PureAtomistic/juliac/build/bin/md_run` with `--trim=safe` (Julia 1.13, build tool environment shared with PureMLIP), runs 100 steps on the tiny checkpoint under a timeout, and requires the trajectory and the extxyz final frame to equal the untrimmed `PureAtomistic.run_md` bit for bit. It runs only with `PUREATOMISTIC_JULIAC_BUILD=1`. A trimmed binary takes no `-t`; threads come from `JULIA_NUM_THREADS`. Reason: the whole-program trim proof and the binary's numerics both need a build.
- A trimmed program cannot print a `LazyString` or call a function with an abstractly typed argument. `PureAtomistic/juliac/entry.jl` renders an exception message by iterating the `parts` of its `LazyString`: `String` parts are printed, any other part goes through `jl_static_show`; other exceptions are shown with `jl_static_show`, and every failure exits with code 1. The build writes a `LocalPreferences.toml` with `banner = false` for StrictMode for its duration, so the binary prints no StrictMode banner whatever load path it runs under. Reason: `lazy"..."` messages stay readable, and the binary stays silent on success.
- PureAtomistic's gates: `test_layers` and the public-access item above; `Aqua.test_all(PureAtomistic)` with every sub-check; ExplicitImports checks for stale and non-owner explicit imports and self-qualified accesses; per module, TrimCheck items (tag `:checks`) for the exported functions, `@test_noalloc` items for the `!` functions, concrete return-type checks and TypeContracts contract checks. StrictModeTest's `test_calls` sweep is not applied to PureAtomistic; `test_compiled` and `audit` serve the StrictMode policy item below. The package source declares its dependencies with `import`, so Aqua's stale-dependency check sees each one used. Coverage rows live in `PureAtomistic/test/coverage/thresholds.toml` and the mutation entries in `PureAtomistic/test/mutation/mutations.toml`, under the same rules as PureMLIP's; the mutation runner copies the sibling `PureMLIP/` Project.toml and `src/` next to its temporary copy so the `[sources]` path resolves.
- Run the suite: `PUREMLIP_CHECKPOINT_DIR=<dir> julia --project=PureMLIP -e 'using Pkg; Pkg.test()'`, and `julia --project=PureAtomistic -e 'using Pkg; Pkg.test()'` for PureAtomistic. Tests download checkpoints by URL and verify SHA-256; `PUREMLIP_CHECKPOINT_DIR` names a local cache directory of your choice.
- `src/precompile.jl` (included last) runs a PrecompileTools workload over the spherical-harmonics, Clebsch-Gordan, Wigner and e3nn entry points and over model loading and evaluation: it loads a tiny checkpoint that `src/tiny_checkpoint.jl` writes in memory (a ZIP64 archive and pickle of the supported architecture with 2 channels), builds a `MACEModel{Float64}` and calls `mace_energy_forces`. No file or network access, so the workload is reproducible. The tiny checkpoint passes the same `MACEModel` validation as a real one. Reason: it moves first-call compile time into package precompilation. Measured on one host: with the workload the first `mace_energy_forces` call takes 0.3 ms and `MACEModel` construction 37 ms; without it, 1.9 s and 2.6 s.
- The neighbor list is an own cell list (`src/model/neighbors.jl`), so `PureMLIP.Model` adds no dependency to `[deps]`. Reason: the list is part of the package and keeps `[deps]` small.
- The `:latency` item runs `test_latency(:PureMLIP; calls = [...])` in measure-only mode: it records load and first-call time in fresh child processes and never fails on time. Reason: wall-clock budgets depend on the host. On a pinned host, add a budget: `test_latency(:PureMLIP; calls = [...], max_load_ms = 50, max_first_call_ms = 5)`; choose the numbers from that host's own baseline. With StrictModeTest >= 0.5.6 the first-call figure includes the first call's compilation (`e3nn_wigner_3j(1, 2, 3)`: 0.3 ms against 0.35 ms by `time_ns`).
- CI runs both packages (a `package: [PureMLIP, PureAtomistic]` matrix axis in `CI.yml`, the coverage job and `mutation.yml`) on Julia 1.12 and 1.13 with `check_bounds: 'yes'`. PureAtomistic jobs set `PUREMLIP_CHECKPOINT_DIR` to a runner-temporary directory, because its tests load PureMLIP checkpoints.
- Documentation: each package builds its own DocumenterVitepress site in `docs.yml`. PureMLIP's site is deployed at the root of `gh-pages`; PureAtomistic's is deployed under `PureAtomistic/` (`dirname = "PureAtomistic"` in `DocumenterVitepress.deploydocs` and a matching `deploy_url` in `MarkdownVitepress`, which sets the VitePress base path). The two jobs run one after the other (`max-parallel: 1`) because both push to `gh-pages`. Reason: `deploydocs` replaces only the folder it deploys, so the sites coexist.
- Items tagged `:pureblas` (`PureMLIP/test/pureblas/`) run in their own Julia 1.13 environment, with `PureBLAS.activate()` called once in `runtests.jl`, and are filtered out of the main suite. They check the LAMMPS references within the main suite's tolerances in both precisions, agreement with OpenBLAS values computed in a child process that never loads PureBLAS (`10·eps(T)·1280` relative), and `@test_noalloc` of both evaluation entry points. The environment pins PureBLAS by `[sources]` URL and commit; moving the pin is a deliberate change. CI runs it in a Julia 1.13 job. Reason: PureBLAS requires Julia 1.13 and is unregistered, so it cannot join the main test environment, and PureMLIP must stay correct and allocation-free when PureBLAS routes its matrix products.
- GPU items carry the tag `:gpu`, live in `<pkg>/test/gpu/`, and the main suites filter them out. The backend comes from `PUREMLIP_GPU_BACKEND` (`CPU`, `Metal`, `CUDA` or `AMDGPU`); run them with `PUREMLIP_GPU_BACKEND=<backend> julia --check-bounds=yes --project=<pkg>/test/gpu/<backend in lower case> <pkg>/test/gpu/runtests.jl`. They run on each GPU machine before every push. CI has no GPU: the job "GPU kernels on the KernelAbstractions CPU backend" runs the same items with `PUREMLIP_GPU_BACKEND=CPU` in `<pkg>/test/gpu/cpu/` (KernelAbstractions and no vendor package) on Julia 1.12 and 1.13 with `--check-bounds=yes` and coverage. Items that only make sense on a GPU skip themselves on the CPU backend. Metal runs Float32 only; the CPU backend and GPUs with Float64 run both precisions. Reason: the kernels are one code base, so the CPU backend catches regressions and measures coverage, while the GPU runs prove the device itself.
- The GPU path is exempt from TrimCheck and the juliac items. The CPU gates are unchanged, and `PureMLIP/bench/ab_compare.jl` shows the CPU path's speed unchanged at the end of each phase. Reason: KernelAbstractions needs the full compiler at run time.
- The extension files are gated by their own coverage and mutation tables: `check.jl --root ext/<package>GPUExt --thresholds thresholds_gpu.toml` judges the `ext/` files with the CPU-backend run (rows in `test/coverage/thresholds_gpu.toml`), and `MUTATION_SUITE=gpu` runs `test/mutation/run.jl` over `mutations_gpu.toml` with `test/gpu/runtests.jl` on the CPU backend. Each task that adds an `ext` file adds its row.
- Per-file line coverage is gated: run the suite with `Pkg.test(coverage = true)`, then `julia --project=PureMLIP/test/coverage PureMLIP/test/coverage/check.jl`. It compares each `src/**/*.jl` file with its row in `PureMLIP/test/coverage/thresholds.toml` and fails on any file below its row or without one, so a new source file needs a row. CI runs it in a Julia 1.13 job. Ratchet rule: raise a row when coverage rises; lowering a row needs the user's approval. A file with no coverable lines scores 1.00 and has row 1.00, so code added to it later must be covered. Reason: coverage cannot erode silently.

## Oracles and tolerances

- Oracles (reason: each is independent of the code under test): e3nn-core-rs fixtures (MIT/Apache, tolerance 1e-10); the e3nn-core-rs radial fixture (MACE radial functions, 1e-10); LAMMPS-MACE energies, forces and virial for five structures, committed as JSON (target 1e-6 eV for the Float64 models); llmlip.rs inspection of MP-0b3 (Apache-2.0); the Wigner-3j tables stored in MP-0b3; WignerSymbols; ForwardDiff; finite differences; quadrature orthonormality. LAMMPS runs only on the machine that regenerates the JSON; CI never runs LAMMPS.
- A test compares against an independent oracle, not against the code under test. Reason: a check that shares code with what it checks cannot catch that code's bugs.

### Tolerance policy

- Every numeric comparison in a test states its oracle and a tolerance justified by exactly one of: (a) the oracle's own stated tolerance (e3nn-core-rs fixtures: 1e-10); (b) a rounding bound `c · eps(T) · N`, with the constant `c` and the operation count or condition `N` written in a comment next to the comparison; (c) a measured margin: the largest error observed, written in the comment, with the tolerance at most 100 times that and normally 10 to 20 times. Reason: a tolerance with no stated source is either too loose to catch a wrong convention or too tight to survive another platform, and nobody can tell which.
- A tolerance is never raised to make a test pass. A failure above the stated bound is investigated; the comment and the number change together only when the measurement or the bound changes. Reason: a loosened tolerance hides exactly the error the test exists to find.
- A threshold that separates two populations (the `1e-13` zero threshold of `e3nn_wigner_3j`) is justified as a measured gap: the largest value on the low side and the smallest on the high side are both written down, and the threshold lies between them. The tests assert the gap at the measured extremes. Reason: a threshold with no gap measured is a guess that fails on the next input.
- Equality `==` is used where the computation is exact by construction (copies, integer arithmetic, a value passed through unchanged). Reason: any tolerance there would only hide a defect.
- The mutation smoke check (`PureMLIP/test/mutation/`, run by hand or by the `Mutation` workflow) applies one deliberate bug at a time from `mutations.toml` to a temporary copy of `PureMLIP/`, runs the full suite, and classifies each run: killed (an item matching `expect` fails), killed elsewhere (items fail, none matching `expect`), survived (the suite passes) or invalid (the package does not load or the suite never reports). It first runs the unmutated package as a control. A survivor or an invalid run fails the check; a survivor is a missing test and gets one. Each `find` string occurs exactly once in its file, so a stale entry fails the run instead of doing nothing. New math gets mutations: every new formula, update rule or numerical decision (a sign, a factor, a step order, an acceptance test) gets at least one, killed by its intended item. Code that is only moved, renamed or wired up (a parser, a CLI, a declaration file such as `src/PureMLIP.jl` or `src/precompile.jl`) gets none; when it moves, the `find` strings of existing entries are updated so none goes stale. Reason: coverage shows that a line ran, not that a test would notice it being wrong.

## Measured speed and memory

- Speed claims rest on interleaved A/B ratios (`PureMLIP/bench/ab_compare.jl`: head and base alternate in child processes, one thread, a calibration loop discards disturbed pairs), never on absolute times. Reason: the host drifts run over run, so only a ratio taken within one interleaved run is comparable. The records are the JSON files in `PureMLIP/bench/results/`.
- Workspace memory (`Base.summarysize`, `cu_bench(14)`: 10,976 atoms, 78 edges per atom, workspace construction; the `MACEWorkspace` is built for the one element, Cu): a `MACEWorkspace` takes 91,613 bytes per atom in Float64 and 45,812 in Float32 (89,557 and 44,784 without its contraction matrices); a `MACEEnergyWorkspace` takes 14,402 and 7,205. A `MACEWorkspace` with `nchunks = 4` takes 112,029 bytes per atom in Float64 and with `nchunks = 8` 148,560, at the default `edge_chunk` of several chunks (1024); at `edge_chunk = 4096` they take 139,955 and 204,411 (137,899 and 202,356 without the matrices). Each further receiver chunk adds 25.5 MB of edge-chunk buffers at `edge_chunk = 1024` (102 MB at 4096), 15 MB of block buffers at `block = 256`, 15 MB of symmetric-contraction scratch (0.8 MB for the per-atom kernel, 14.2 MB for the matrix products over 64 atoms) and 4,096 bytes per atom. The symmetric-contraction matrices take 22.6 MB per element in `elements` in Float64 (11.3 MB in Float32) for MACE-MPA-0, independent of the atom count and shared by the chunks. Pools of buffers that share one `Memory` are counted once. Reason: a quoted figure has to equal what the process holds.
- Speed against LAMMPS-MACE (`cu_bench(5)`: 500 atoms, MACE-MPA-0, one thread each, median of five interleaved rounds, one force evaluation): with OpenBLAS, `mace_energy_forces!` takes 1.10 s in Float64 and 0.62 s in Float32 against LAMMPS' 3.25 s and 2.37 s (ratios 2.96 and 3.83). The round-to-round spread of the ratio is 2.56 to 2.98 (Float64) and 2.97 to 4.89 (Float32) on a host shared with other work. PureBLAS has not been timed against LAMMPS. Its effect is an interleaved A/B ratio (`ab_plan_total_pureblas_mac.json`, `cu_bench(5)`): `mace_energy_forces!` at commit 735f470 with PureBLAS active is 2.39 times faster in Float64 and 3.05 times faster in Float32 than at commit 596b5b2 on OpenBLAS.
- LAMMPS is run only at sizes that keep its resident set under 12 GB (`cu_bench(5)` peaks near 10 GB in Float64); `cu_bench(14)` is measured on the Julia side alone.
- Speed on the GPU (`PureMLIP/bench/gpu_compare.jl`, MACE-MPA-0, Float32, Apple M6 with Metal, 7 interleaved rounds, one process per arm per round, arm order rotating; speed-up is reference time over the Metal time, quoted as [min, max] over the rounds; records `PureMLIP/bench/results/gpu_compare_*metal*.json`; rounds are discarded when swap use grows or the calibration loop disagrees, at 10 % within a child and 10 % between children, looser than the 3 % and 1 % of `ab_compare.jl` because the single-thread child showed 3.5 to 5 % spreads on this host, and the multi-threaded CPU arm is left out of the pair comparison and allowed 50 % within its own child, because its single-thread calibration right after the 6-thread burst reads 15 to 130 % off): one energy + forces + stress evaluation takes 0.0698 s at `cu_bench(5)` and 1.354 s at `cu_bench(14)` (10,976 atoms), against threaded PureMLIP on the CPU (6 threads, `-t 6,0 --gcthreads=1,0`, 1 BLAS thread, PureBLAS, Float32) at 0.0869 s and 2.113 s: 1.25 [1.24, 1.30] and 1.56 [1.53, 1.64]. The MD step is 0.0700 s and 1.354 s against the same threaded CPU step at 0.0903 s and 2.232 s: 1.29 [1.27, 1.45] and 1.65 [1.60, 1.70]. The device's allocated memory is 0.35 GB at `cu_bench(5)` and 1.58 GB at `cu_bench(14)` (Metal `currentAllocatedSize` after the timed calls, checked against a known 256 MiB allocation at start-up), the threaded CPU's maximum resident set 1.7 GB and 2.2 GB. The status read of a device step costs a median 0.2 ms (0.3 % of the step; mean of the per-round differences 1.4 ms, because the step that reads is about 3 ms slower in 3 of 7 processes, and the reference step shows the same high mode, so it is process jitter) at `cu_bench(5)` and is not measurable at `cu_bench(14)` (-0.05 % of the step, spread of +-0.14 %).
- Speed against fastatomstruct's XLA CPU backend (unpinned, Float32, built and run outside the repository): 0.437 s and 6.2 GB at `cu_bench(5)` (Metal 6.25 [6.19, 6.31] times faster) and 1.99 s and 22.8 GB at `cu_bench(8)`, the largest cell that fits in this machine's 32 GB (Metal 0.250 s, 7.96 [7.88, 8.38] times faster). At `cu_bench(9)` (2,916 atoms) it does not fit. The criterion is the external program's memory guard (free memory under 6 GiB, or swap use growing by more than 1 MB) and the extrapolation of 11.1 MB per atom measured at `cu_bench(8)` to about 32.5 GB against 34.4 GB of physical memory; it was stopped at 24.7 GB maximum resident set. The Metal evaluation takes 0.352 s and 0.79 GB there. The guard runs at `cu_bench(9)` grew swap use by about 161 MB (first full evaluation run) and 73 MB (second), about 234 MB in total (a probe before the runs grew it by about 364 MB), on a host that already held about 16 GB of swap; they are the untimed pass that finds out whether the program fits, no timed number came from them, and no kept round saw swap growth. Single probes at `cu_bench(6)` (0.74 s, 9.9 GB) and `cu_bench(7)` (1.21 s, 15.4 GB) have no Metal counterpart and no speed-up.

- Trailers: `Assisted-by: Claude <model> <noreply@anthropic.com>` and `Claude-Session: <url>`. Reason: they record agent assistance and the session.
