# PureMLIP and PureAtomistic GPU Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run MACE molecular dynamics with the whole step on the GPU (Metal, then CUDA, then AMD) from one KernelAbstractions code base in package extensions. Every CPU validation passes on each GPU, PureMLIP beats each GPU's named reference, and the vacancy-diffusion campaign becomes affordable.

**Architecture:** The core packages gain only binary-free stubs (`device_model`, `device_neighbor_list`, `device_workspace`, `device_result`, `device_potential`, `to_device`), each with a fail-fast fallback. `PureMLIPGPUExt` and `PureAtomisticGPUExt` (trigger: KernelAbstractions) hold the device types and kernels. The device path mirrors the CPU pipeline. Edges are sorted by receiver as CSR, and a reverse-edge map turns every sender-indexed sum (forces, `dx`) into a gather, so the device path uses no floating-point atomics and every reduction runs in a fixed order. Matrix-shaped stages call `mul!` on device arrays (vendor BLAS) wherever the stage profile shows that it pays. One MD step runs entirely on the device. The host reads back only a small status word and the scalars named below, and it copies arrays only at the output interval.

**Tech Stack:** Julia 1.12/1.13; KernelAbstractions 0.10 (weak dependency); Metal.jl 1.12+, current CUDA.jl, AMDGPU.jl 2.9+ (test and bench environments only, versions from spec 2026-10-30 section 14); StrictMode/StrictModeTest 0.5.10, TypeContracts 0.14, TestItemRunner; Chairmarks for timing.

**Spec:** `docs/superpowers/specs/2026-11-06-gpu-design.md` (every line). Also spec 2026-10-30 section 7 items 4–5 (the campaign) and section 14 (KernelAbstractions 0.10 decision), and the plan 5 Task 12 records `PureAtomistic/bench/results/md_{nve_conservation,thermostat_check,vacancy_hop}.json`.

## Global Constraints

- **Weak dependency only.** KernelAbstractions is in `[weakdeps]` of both packages: `[extensions] PureMLIPGPUExt = "KernelAbstractions"` and `PureAtomisticGPUExt = "KernelAbstractions"`, with `[compat] KernelAbstractions = "0.10"`. All GPU code lives in the extensions. No `_jll` package or artifact enters either core closure, and the vendor packages appear only in the `test/gpu/<backend>/` and `bench/gpu/<backend>/` environments.
- **Hardware-agnostic first.** The backend comes from `get_backend` of the caller's arrays. Every device entry point checks that all of its array arguments share one backend and the model's element type. Vendor-specific code exists only for a measured workaround or tuning, and the measurement goes in the commit body and in `bench/results/`.
- **The CPU path is unchanged in results and speed.** The CPU suites pass unchanged, including "forces: one chunk reproduces the stored reference bits". At the last commit of each phase, `PureMLIP/bench/ab_compare.jl` against base `9df39ef` (cases `5:64,5:32`) must give a median time ratio of at most 1.02, reported as a speed-up with its [min–max] range.
- **Precision.** Metal runs Float32 only. CUDA and AMD run Float32 and Float64 where the hardware supports Float64. Device code never converts Float32 to Float64: `StrictMode.conversion_report(ext; from = Float32, to = Float64)` is empty for both extensions.
- **Correctness oracles.** The five LAMMPS reference structures (plan 3), finite-difference forces, and the CPU result in the same precision. GPU-against-CPU agreement uses bound (b) of the tolerance policy: `10·eps(T)·1280` relative to the largest magnitude, separately for the energy, the node energies, the forces, the virial and the stress. N = 1280 is the largest inner dimension of any matrix product, as in `forces_tests.jl`. When a device transcendental's documented ULP error enters, the comment adds it with its source. A failure is investigated; the bound is never raised.
- **Per-step transfers.** No array is copied between CPU and GPU in any MD step. Each step reads back at most one status word (4 × Int32: rebuilt, capacity overflow, sampler cap reached, unknown element). The barostat adds one scalar (the pressure). An observer that asks for the kinetic energy adds one scalar. The step-time cost of each readback is measured and stated (Task 11). Arrays are copied only at the output interval (`copy_state!`).
- **Random numbers are drawn on the GPU.** The generator is Philox4x32-10 (Salmon et al., SC'11), counter-based. Each step's key is one `rand(rng, UInt64)` drawn on the host from the simulation's `rng` and passed as a kernel argument. GPU thermostat trajectories match the CPU statistically, not bit for bit. A seeded GPU run reproduces itself bit for bit on the same device.
- **Trim.** The GPU path is exempt from TrimCheck and the juliac items. The CPU gates are unchanged.
- **Rules from AGENTS.md:**
  - Tests come first.
  - Fail fast, with `lazy"…"` messages. Prefixes: `"model: "` for the PureMLIP core stubs, `"gpu: "` for `PureMLIPGPUExt`, and `"pureatomistic: "` for PureAtomistic and its extension. `@test_throws "message"` checks every error.
  - Generic indexing. Device entry points call `Base.require_one_based_indexing` and accept views of device arrays, which the tests exercise.
  - No `@inbounds` in a kernel without a measured end-to-end win, a local proof of the index range, and a test. The GPU suites run with `--check-bounds=yes`.
  - Concrete struct fields.
  - Coverage rows for every new file.
  - Mutations for new math only. Each kernel that computes a formula, the RNG, the device samplers, the Bussi and Berendsen device updates and the cell list each get at least one, killed by the intended item. Code that is only moved or wired up gets none.
  - Comments are in the present tense and never mention plans or tasks.
- **Speed claims.** Speed-up = reference time ÷ PureMLIP time, as the median [min–max] of 7 interleaved rounds, with a named reference and matching precision. Peak GPU memory (and peak RSS for CPU arms) sits beside every speed figure. The target is judged at `cu_bench(14)` (10,976 atoms), and `cu_bench(5)` is reported too.
- **GPU tests are opt-in.** Items tagged `:gpu` live in `PureMLIP/test/gpu/` and `PureAtomistic/test/gpu/`, and the main suites filter them out. To run them: `PUREMLIP_GPU_BACKEND=<Metal|CUDA|AMDGPU> julia --check-bounds=yes --project=<pkg>/test/gpu/<backend> <pkg>/test/gpu/runtests.jl`. They run on each GPU machine before every push, and CI stays CPU-only.
- **Machines.** Name them only "the Apple M6", "the x86 machine" and "the AMD GPU machine"; no host names or local paths go in tracked files. On the x86 machine, timing runs with the clock locked by `fleet_freqlock.sh` (outside the repositories), verified under load before and after each window. fastatomstruct is built and run only outside the repositories, and its source is never read. Its timings stay outside the repositories and are summarized in the GPU spec.
- **No Python.**
- **Commits.** Commits use the AGENTS.md trailers and are pushed to `main` after the GPU suites pass on the machine of the phase.

## Review Focus

1. **Unwrapped positions far outside the cell** (a diffusing atom many cell lengths away after a long run, or a triclinic cell). The device neighbor list and forces equal those of the wrapped configuration within the bound. Test in Task 7.
2. **Edge-capacity overflow mid-run on the device** (a hot step packs more edges than the list holds). The potential regrows the list and workspace once, logs the regrowth, and the step's forces equal a fresh evaluation. Test in Task 8.
3. **Mixed arguments**: host and device arrays mixed, arrays from two backends, a Float64 model on Metal, or an `OffsetArray` around a device array. Each fails before any launch with a message that names the problem. Test in Task 3.
4. **Tiny systems**: one atom, two atoms out of range (zero edges), or a cell thinner than the cutoff. The energy is the sum of `E0`, the forces are exactly zero, and the edges equal the CPU's. Tests in Tasks 6 and 7.
5. **An element that is not in the device model** (an atomic number outside `elements`, found on the device). The evaluation throws `"gpu: atomic number … is not among the device model's elements"` and does not return a wrong energy. Test in Task 5.

### Task 7: Neighbor list built on the device

**Files:**
- Create: `PureMLIP/ext/PureMLIPGPUExt/neighbors.jl`.
- Test: `PureMLIP/test/gpu/neighbor_tests.jl`.

**Interfaces:**
- `device_neighbor_list(positions, cell, r_cut; skin = 0, extra_capacity = 0) -> DeviceNeighborList` and `neighbor_list!(nl::DeviceNeighborList, positions, cell) -> nl`.
- The list is a cell list whose grid cells are at least `r_cut + skin` wide, with the same reach rule as the CPU list for thin cells. It is built by counting sort: bin, then an exclusive scan, then scatter. A second pass over each receiver's neighbor cells counts its edges, a scan gives `row_ptr`, and a third pass fills the edges. `reverse` is built by a search within the sender's row.

It writes `status[1]` (rebuilt) and `status[2]` (overflow). The host reads the status once and throws `ArgumentError(lazy"gpu: $m edges exceed the capacity $capacity")`, after which the list must be rebuilt with `device_neighbor_list`.

### Task 8: GPU MD step: potential, velocity Verlet, transfer rules

**Files:**
- Create: `PureAtomistic/ext/PureAtomisticGPUExt/{potential.jl, motion.jl}`.
- Modify: `PureAtomistic/src/driver.jl`, adding `kinetic_energy(sim::Simulation) = kinetic_energy(sim.system)` and `temperature(sim::Simulation; dof)` as methods of the `Systems` functions.
- Test: `PureAtomistic/test/gpu/md_step_tests.jl` and the CPU `test/verlet_tests.jl`.

**Interfaces:**
