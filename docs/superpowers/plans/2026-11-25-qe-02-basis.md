# QuantumEngine step 02 (basis sets) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the `QuantumEngine.Basis` module: the whole-file Gaussian94 `.gbs` reader with its ECP sections, a reader for the oracle's ECP JSON format, basis-name resolution and the search path, the shipped Basis Set Exchange data, the molecular basis (`Shell`, `BasisSet`) with the oracle's Cartesian component order and normalization, and the element table extended to every element the data names. Nothing of steps 03–17 is in scope; ECP integrals stay with step 14.

**Architecture:**
- One module `Basis` in `QuantumEngine/src/basis/`, entry file `Basis.jl`, split into files by responsibility (geometry helpers, types, `.gbs` reader, ECP JSON reader, names, search, build).
- Layer graph after this step: `Basis => (IO, System, Units, Errors)` (default of D7). Basis cleans its lines with `IO.input_line` and logs through `IO.Logger`, as every module above `IO` does.
- The `.gbs` file is parsed whole into `Dict{String,ElementBasis{Float64}}`, once per `build_basis` call, so a grammar error anywhere in the file is reported; the angular-momentum limit is applied when a shell is placed on an atom (default of D2).
- A basis name resolves to exactly one file: stems outer, directories inner, the first existing file wins; a parse error or a missing element is an error, never a reason to try the next file.
- `Shell` stores raw × contraction-renormalized coefficients; the per-component primitive norm is the consumer's (03). `BasisSet{T}` is parametric; the reader is Float64 and `build_basis(mol, name, T)` converts the data to `T` before renormalizing.

**Tech Stack:** Julia 1.13; Base (`eachline`, `Regex`, `split`, `tryparse`); StaticArrays 1.9 (`SVector`); JSON.jl (entered in step-01 Task 10, used through the public route recorded under step-01 D2); StrictMode 0.5.21. No new dependency (Evidence E7). Tests: TestItems, StrictModeTest, TrimCheck 0.1.5, OffsetArrays, Aqua, ExplicitImports.

**Spec:** `02-basis.md` of the QuantumEngine rewrite specs, with `00-overview.md`, `PLAN.md` and `99-open-questions.md` (its "Decisions (2026-11-25)" and "Decisions needed" sections). The specs live outside the repository (step-01 D19); the coordinator hands them to each implementer and reviewer with this plan. The oracle checkout is named by `QUANTUM_ENGINE_ORACLE_SRC`; it is read-only, never built, and its code is read to learn behavior, never copied (Apache-2.0).

**Evidence.** The research behind this plan exists only in a session scratch directory. Every figure the tasks rely on is in the appendix "Evidence" with its command or source line. A task that needs a figure not in the appendix measures it again and records it in its commit body.

**Preconditions.** Step 01 is complete (its Task 15 review approved): `Errors`, `Units`, `System`, `IO` (with `input_line`, `Logger`, `log_print`) and `Input` exist, JSON is a dependency, and `test/oracle/harness.jl` and `capture.jl` exist. - **Name trap.** Inside `QuantumEngine` and its `IO` module the name `IO` is the submodule, so stream arguments are annotated `Base.IO`. Tests never write `using QuantumEngine.IO` as a bare statement: after it, `IO` is ambiguous between Base and the submodule (`UndefVarError: IO not defined … also exported by Base`, measured on Julia 1.13.4). They write `using QuantumEngine.IO: name1, name2` or qualify as `QuantumEngine.IO.name`.
- **Logging.** `IO` and every module above it log through `IO.Logger` (spec 01); `Errors`, `Units` and `System` sit below `IO` and do not print. The quality item "no bare printing to stdout" scans `QuantumEngine/src` outside `src/io/logger.jl` for the regex `\b(println|print|printstyled)\((\"|lazy\"|stdout)` and for `@show`, and fails on any match.
- **Messages.** Error and warning messages are stored as `LazyString` (field type `msg::LazyString`), so that an interpolated `lazy"..."` message is not converted to a `String` when the error is built. Constructors take any `AbstractString` and convert with `LazyString(msg)`. A message is printed only by walking `msg.parts` in one helper, `Errors._print_message(io::Base.IO, m::LazyString)`, which writes each part with a call on its concrete type (`String`, nested `LazyString`, `SubString{String}`, `Symbol`, `Char`, `Bool`, `Int`, `Float64`) and throws for any other part type. `print(io, ::LazyString)` is never called: measured during Task 1, it fails the typestable and noboxing proofs. The `showerror` methods and `InputWarning`'s `show` print through this helper, and the juliac entry prints an error with `showerror`, so through it too.
- **StrictMode.**
  - `@strict_policy (:typestable, :noalloc)` is the last statement of every module, preceded by the comment `# Last statement: the policy checks the methods defined above it.`
  - A module imports from StrictMode only the macros it uses: `using StrictMode: @strict_policy`, plus `@strict_exempt` in a module that has an exemption (ExplicitImports' stale-import check fails otherwise).
  - `@strict_exempt` is allowed only for entry points and allocating constructors, narrowed to `:noalloc`, with a present-tense reason naming its kind. The one exception is the message rendering below, which is also exempt from `:noboxing` (user decision 2026-11-25: "keep it fast and trim-compatible"). Each exemption names its function, as `PureAtomistic/src/io/IO.jl` does: `@strict_exempt :noalloc read_xyz reason = "entry point: xyz reader"`. An allocating helper that only an entry point calls is exempted by name with a reason naming that entry point. Every allocating constructor is exempted in the task that writes it: `@strict_exempt :noalloc <Type> reason = "entry point: <kind> constructor"`, plus `@strict_exempt :noalloc :_ reason = "entry point: keyword body of the <Type> constructor"` where a constructor has keyword arguments.
  - `Base.showerror` methods and `InputWarning`'s `Base.show` are swept with the module that defines them (measured: `test_compiled(Errors)` and `audit(Errors; sweep = true)` judge `showerror(::IOBuffer, ::InputError)`). Each is written from single-argument `write`/`print` calls, not one varargs `print(io, a, b, c, …)`, prints the message through `Errors._print_message` (Messages), and is exempted `@strict_exempt :noalloc reason = "entry point: renders the error message"`. Measured: with the `LazyString` field, `print(io, e.msg)` fails typestable and noboxing; the parts walk passes typestable and TrimCheck, but reading `parts::Tuple` at a runtime index still boxes (`tuple.jl:33`). So `_print_message`, every `showerror` and `InputWarning`'s `show` are exempted by name from `:noalloc` and `:noboxing`, reason "entry point: renders a LazyString message, whose parts are an abstract Tuple". They run only on the error path. While every function in `Errors` is an exempted entry point, the noalloc scan judges nothing; its count assertion is `@test_broken` until Task 2 sweeps `Units`, which turns it back into `@test`.
  - The methods `@enum` writes into the defining module (`Base.Enums.namemap`, `Base.Enums._enum_hash`, `instances`, `typemin`, `typemax`; measured on Julia 1.13.4) are skipped by `other_function` in `test/strict/check.jl`, with a comment saying that `@enum` writes them.
  - The items "StrictMode policy holds in QuantumEngine" and "StrictMode gates reject the failing control" run `test/strict/check.jl` in a fresh process after `test/strict/workload.jl`.
  - Each task adds its entry points to the workload, so that every exempted function has a compiled specialization.
  - If a sweep that a gate requires to be non-empty comes back empty, stop and report; never drop the assertion.

  - An ECP section holds exactly `lmax + 1` channels, so it ends after the last row of its last channel; the next line must be a header, a `****` line, a blank or comment line, or EOF. Every shipped ECP section ends at a header, a blank line or EOF (plan review's awk over the 12 ECP files, 542 sections, 0 exceptions; not re-run). The block-closing count above was re-run: 2873 basis blocks, 542 ECP sections, 0 blocks not closed by `****`.
  - Shell letters S P D F G H I map to l = 0…6, with `SP` handled as S then P, matched case-insensitively; `L` and every other letter are unknown.

  - Each shell is checked once with `contraction_renorm` on its Float64 data: a zero norm is a parse error with the shell's line.
  - ECP channels are titled `<L> potential` first (l = lmax, the local channel), then `<k>-<L> potential` for k = 0…lmax−1, where L and k are shell letters (E12). The title is matched case-insensitively and gives the channel's `l`. Each channel is a count line, then `power exponent coefficient` rows.

### Task 8: Normalization against the closed form

**Precondition:** D8 answered; Task 6 done.

**Files:** Create `test/basis_norm_tests.jl`.

- [ ] **Step 0: Write the derivation into the test comment before any run.** D8 (A) makes every operation correctly rounded (`+`, `*`, `/`, `sqrt`), so the count is pure rule (b), u = eps(T)/2:
  - The base `b = 2√(α_i α_j)/(α_i+α_j)` takes ≤ 3.5u (product, sqrt, sum, division). `b^{l+1}` by l multiplications times `sqrt(b)` carries the base error times p = l + 3/2, plus l + 2 roundings (l multiplications, the sqrt, the final product): ≤ (3.5p + l + 2)u.
  - Each term `c_i c_j t_ij` adds 2u.
  - The naive sum of n² terms adds (n² − 1)u, relative to Σ|terms| = κ·D.
  - So the sum D carries (n² + 4.5l + 8.25)·u·κ, k_D = n² + 5l + 9 after rounding up (the bound Task 2's STO-3G item uses for the factor).
  - The sqrt, the division and the final scaling add 4u + 2uκ.
  - Total, first order: |S − 1| ≤ (n² + 4.5l + 14.25)·u·κ, so k = n² + 5l + 15 after rounding up, used as `γ_k = k·u/(1 − k·u)`.
  - If the implementer's count differs, the larger count is used, written in the comment, and decided before the run. The bound is never fitted to the data.
- [ ] **Step 1: Write the items.**
  - `"normalization (closed form)"` (the spec's item).
